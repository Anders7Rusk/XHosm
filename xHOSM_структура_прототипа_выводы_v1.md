# xHOSM — почему структура прототипа такая

Выводы по структуре черновика `index.html` (структура «Клиент и сервер»).
Основание — материалы этапов 1–2: боли, сценарии работы и интерфейса, 16 гипотез.
Дата: 18.09.2026.

---

## 1. Главный вывод: работа L3 — объектная, поэтому и ось интерфейса объектная

Поддержка работает не «с функциями», а с конкретным клиентом и его сервером: «у Ромашки отвалился сервер», «перезапустить romashka-01». Путь любого обращения один:

```
найти клиента → найти его сервер → понять состояние → сделать действие → увидеть результат
```

Отсюда ось: **Поиск → Клиент → Сервер**. Остальное — слои поверх этой оси:

```
Поиск (CRM ID / UID / домен / клиент)
   └─ КЛИЕНТ → его серверы → СЕРВЕР
        СЕРВЕР: Обзор · Служба · Логи · История (+ действия: остановить, перезапустить)

Рабочий стол — слой «смена»: очередь операций · требует внимания · мои клиенты
```

## 2. Вход — поиск, а не навигация

Боль: данные разрознены, «где искать — непонятно» (CRM, лицензии, логи — по разным местам). Поэтому главный вход в интерфейс — **омнипоиск по любому идентификатору**: CRM ID, UID, домен, название клиента. Меню слева — вторично: это «мои зоны», а не способ что-то найти.

## 3. Первый экран — рабочее место смены

Вывод из болей: в смене не видно, **что происходит сейчас и за что хвататься**. Поэтому «Рабочий стол» отвечает ровно на эти два вопроса:

- **очередь операций** — что система делает прямо сейчас;
- **«требует внимания»** — что само просит действия (с формулировкой, что сделать);
- **«мои клиенты»** — зона ответственности дежурного;
- **метрики смены** — контекст («12 разобрано, 3 в работе»).

## 4. Статус должен доказываться, а не декларироваться

Самая частая претензия из болей — **«статусам нельзя доверять»**. Вывод: цветной плашки недостаточно. Поэтому у статуса сервера стоят:

- **источник и свежесть** — «проверено агентом 12 секунд назад, источники совпадают»;
- **история смен статуса** — что было, когда и почему («авто → остановлен»);
- **кнопка «перепроверить»** — статус можно оспорить и обновить в один клик.

Статус становится проверяемым, а не «на слово».

## 5. Операции — это процессы, а не записи в журнале

Боль: долгие операции идут «в никуда» — непонятно, работает ли что-то, сколько ждать. Вывод:

- каждая операция — **процесс с шагами**: «шаг 2 из 3 — запуск службы, осталось ≈1 мин»;
- при сбое — **ошибка с причиной и что делать**: «нет места на диске → повторить после очистки»;
- кнопки действий сразу показывают план: «остановка → запуск → проверка, ≈2 мин, тех.окно не нужно».

## 6. Логи и история — на месте объекта

Боль: логи и бэкапы открывались по ссылкам, которые не работали. Вывод: **логи и история живут внутри карточки сервера** — на вкладках, рядом со статусом и действиями, а не «где-то ещё».

## 7. Клиент — это контекст, который должен быть под рукой

Боль: по клиенту всё размазано (лицензии, CRM, договор — отдельно). Вывод: карточка клиента собирает:

- **доступы/лицензии** — самое частое: UID, iikoUser, версия, память/период;
- **его серверы** — список прямо в карточке, не отдельным экраном: путь до сервера короче;
- **договор** — контекст обслуживания;
- **последние операции** — что уже делали.

Базовые вопросы решаются без прыжков в другие системы.

## 8. Сводка: боль → элемент

| Боль из материалов | Что из неё выросло в прототипе |
|---|---|
| Статусам нельзя доверять (DO-1225) | Статус с доказательством: источник, свежесть, история, «перепроверить» |
| Нет прогресса долгих операций (DO-1431) | «Операции сейчас» с этапами; план действий в диалоге |
| Логи/бэкапы по мёртвым ссылкам (DO-899) | Логи и История — вкладки карточки сервера |
| Всё разрознено, в т.ч. CRM (DO-1329) | Омнипоиск + карточка клиента 360° |
| Уведомления не решены (DO-427, с 2019) | «Требует внимания» с формулировкой действия |
| «За что хвататься в смене» | Рабочий стол: метрики, очередь, мои клиенты |
| Массово — по одной (DO-969) | *Отложено: массовость и шаблоны — следующий слой* |

## 9. Чего в черновике сознательно нет — и почему

- **Массовые операции и шаблоны** — это слой поверх оси; сначала проверяем саму ось.
- **Права/роли, локализация, SSO** — не влияют на проверку структуры, отложены.
- **Полная детализация разделов сервера** (лицензии/версии/конфиг/бэкапы) — свёл к каркасу (4 вкладки), чтобы не раздувать проверку.
- **Сравнение со старым интерфейсом** — это обёртка; она станет нужна, когда структура зафиксирована.

## 10. Что этим черновиком проверяем

Ключевые ставки пилота: **поиск** (H2), **доказательный статус** (H4), **прогресс операций** (H3), **рабочее место смены**, **логи внутри** (H6), **клиент 360°** (H10).

Если на людях ось «поиск → клиент → сервер» понятна и статусу начинают доверять — структура верная, наращиваем слоями.
