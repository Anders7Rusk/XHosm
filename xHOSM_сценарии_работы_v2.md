# xHOSM — сценарии работы (полный сбор, v2)

**Что это:** полный набор сценариев работы с xHOSM — как сейчас работают люди: роли, триггеры, шаги, боли, что должен уметь новый интерфейс.
**Состав:** 34 сценария-карточки (SC-01…SC-34): 20 из черновика v1 + 14 добавленных после поиска по Jira и вики. Плюс смежные сценарии (справочно) и карта источников.
**Как собрано:** из документации (AN «Xhosm»: 30 User Stories, 19 Use Cases), инструкций L3S/DEVOPS/IIK/ECOMM/DORMS, регламентов, и описаний сценариев в задачах Jira (DO/IA/SPRT/WEB и др.). Цитаты — дословно, источники указаны у каждого сценария.
**Собрано:** 18.09.2026. Парный документ: «xHOSM_боли_и_проблемы_v2.md» (боли с цитатами); полные тексты US/UC — в «xHOSM_материалы_для_нового_интерфейса_v2.md».

**Легенда частоты:** ежедневно — много раз за смену; часто — несколько раз в неделю; периодически — по запросу/плану.
**Легенда источников:** «US-xx / UC-xx» — стори и юз-кейсы из доки «Xhosm»; «wiki L3S/DEVOPS/… (id)» — страница вики; «DO-xxx / IA-xxx» — задача Jira.

# ЧАСТЬ 1. Ядро (SC-01…SC-20)

## SC-01. Найти сервер клиента
**Роль:** L3 (ядро), аналитики, партнёры · **Частота:** ежедневно, десятки раз
**Когда:** в работу пришла жалоба/заявка клиента — нужно найти его сервер(ы) по любому известному признаку.
**Как сейчас:** поле мультипоиска: вводит значения столбиком (до 1000 CRM ID за раз), система сама определяет тип ввода — номер клиента, UID, адрес, кластер, SQL-сервер, произвольный WHERE-запрос. Ctrl+Enter — поиск; Shift+«Найти» — связанные серверы (нашли Chain — видим его RMS, и наоборот). Результат — таблица ~23 колонки с фильтрами и сортировкой; по умолчанию 25 строк + «Показать все».
**Источник:** US-017; доки §3.7/§3.10; wiki-комментарий про WHERE и геокодинг.
**Боли:** WHERE-синтаксис — барьер для нетехнических людей; поле «Статус» в поиске не используется; после поиска фильтров много, а до — ничего; вход в систему всегда через этот экран.
**Новому интерфейсу:** единый умный поиск: распознавание типа ввода с подсказкой, визуальный «конструктор» условий вместо WHERE, сохранённые запросы, связи Chain↔RMS одним действием, пакетные действия сразу из результатов.

## SC-02. Оценить состояние сервера
**Роль:** L3, L3 Web, инфраструктура · **Частота:** ежедневно, постоянно
**Когда:** первичная диагностика любой жалобы: «сервер не работает / тормозит / не виден клиенту».
**Как сейчас:** строка таблицы (цвет = статус) → клик по домену → детали. Модуль «Статус»: автообновление (Off/20/60/300/900 сек), «Больше информации», «Внутренний порт», «Ревизия». Красная строка — критично мало памяти; жёлтая — метрики ок; красный терминал — версия undefined. Параллельно поддержка держит открытыми Victoria Logs и мониторинги для перепроверки.
**Источник:** доки §3.10; DO-1225; черновик «Анализ зависаний» (L3S).
**Боли:** «статусу тоже увы доверять нельзя» — сервер может числиться запущенным, будучи недоступным; в списке «Auto», при фокусе — «STOPPED» (партнёры открывали ложные тикеты); время актуальности не показано.
**Новому интерфейсу:** достоверность: показывать источник и время последней проверки, историю статуса, отличие «заявлено/подтверждено», честное «данные устарели» вместо тихого вранья.

## SC-03. Перезапуск/остановка сервиса, очистка unsaveddata
**Роль:** L3 (ядро, самый частый сценарий) · **Частота:** ежедневно
**Когда:** обмен «встал», сервис завис, после изменения конфигурации или как профилактика.
**Как сейчас:** модуль «Служба»: отметить сервер галочкой; чекбоксы «Удалить лицензии», «Удалить unsaveddata», «Аварийное прерывание»; время — Сейчас / Очередь / Тех.окно / Через 1–9 ч / ЧЧ:ММ; периодичность D/W/M/Q/Y; кнопки «Перезапуск» (→AUTO) и «Остановка» (→DISABLED). Далее — ждать и проверять статус/логи.
**Источник:** US-001; BR-SVC-001/002; регламент L3.
**Боли:** долгие операции молчат — «процесс занимает длительное время, а никаких подробностей не предоставляется» (DO-1431); terminating до 5 минут без индикации; после нажатия непонятно, встало ли в очередь.
**Новому интерфейсу:** прогресс и этапы выполнения, ETA, причина/инициатор, уведомление о завершении; единый список активных задач по серверу.

## SC-04. Лицензии: «не работает лицензия / API / Cloud»
**Роль:** L3, партнёры · **Частота:** ежедневно
**Когда:** клиент жалуется на лицензии: не проходят заказы по API, красный «Cloud», не пускает в веб-приложение.
**Как сейчас:** модуль «Лицензии»: ввести UID/CRM ID → «Отвязать», «Удалить», «Обновить», «goCRM», «upRevision», «Обнов. кэш». Отдельные ветки: красный Cloud → upRevision + синхронизация UOC (Postman + админка веба), BCrypt → два Groovy-скрипта (до 5 минут, часть рестартит сервер), API-ошибка кэша → обновить кэш лицензий.
**Источник:** US-002/006; wiki: «Красный статус Cloud», «Не проходят доставки/заказы по API», «Проблема BCrypt хэшей».
**Боли:** лечение одной жалобы разбросано по 3 системам (xHOSM → Postman → админка веба); кнопки без пояснений и без обратной связи; «обновить/обновить» вслепую.
**Новому интерфейсу:** диагностический чек-лист «лицензия не работает» в одном месте: шаги по цепочке с состоянием каждого, связь кнопок с результатом, журнал попыток.

## SC-05. Открыть период редактирования документов
**Роль:** L3 · **Частота:** часто
**Когда:** клиенту нужно внести/исправить документы задним числом (учёт, закрытие месяца).
**Как сейчас:** проверка правил (тариф, размер БД, «до 180 дней / более 180 дней», согласования, исключения вроде Армении) → модуль «Конфигурация» → параметр db-period-length-days → «Сохранить» (+ перезапуск).
**Источник:** US-007; wiki: «Открытый период на RMSCloud» (полная матрица правил и согласований).
**Боли:** правила размазаны по страницам и таблицам; часть операций требует согласований (АМ/Ent/DevOps); легко открыть «не туда».
**Новому интерфейсу:** правила и лимиты — прямо у поля: подсказки по тарифу/размеру/срокам, статус согласования, обязательный комментарий, аудит изменений.

## SC-06. Изменить память (Xmx)
**Роль:** L3 · **Частота:** часто
**Когда:** сервер падает/тормозит, ошибки ОЛАП, тяжёлые отчёты; после диагностики.
**Как сейчас:** модуль «Конфигурация» → параметр memory (Xmx), изменение кратно (1.5×/2×), «Сохранить» → перезапуск; контроль по метрикам и статусу.
**Источник:** US-008; DO-343 (ограничение на увеличение), DO-1106; wiki: «Инциденты, связанные с расчётом памяти».
**Боли:** нельзя увеличить «на глаз» (лимиты по тарифам/хостам), нельзя уменьшить без подтверждений; калькулятор RAM в новом GUI убран — правила останутся, подсказок нет.
**Новому интерфейсу:** рекомендации по значению, объяснение лимитов и последствий, история изменений памяти, безопасные кнопки 1.5×/2×.

## SC-07. Обновить версию (патч, downgrade)
**Роль:** L3, инфраструктура · **Частота:** часто/планово
**Когда:** плановые обновления, патчи, откат проблемной версии.
**Как сейчас:** модуль «Версия»: выбрать версию, Branch, Beta, Бренд, Front/Office; флаги «Downgrade», «Unlock», «Rapid»; время (сейчас/очередь/тех.окно). Проверка открытых смен; выполнение; контроль по логам.
**Источник:** US-010–012; DO-1431; DO-1936; wiki: «Про версии и обратную совместимость».
**Боли:** блокировка «обновление нельзя» при открытых сменах, даже когда фронт не меняется (DO-1936); процесс обновления без деталей; флаги-«лазейки» (Rapid без бэкапа) без объяснения рисков.
**Новому интерфейсу:** прозрачный процесс по этапам с ETA; блокировки с объяснением «почему» и способом разблокировать; риски флагов человеческим языком.

## SC-08. Логи: посмотреть, найти, скачать
**Роль:** L3, L3 Web, разработка · **Частота:** постоянно при разборах
**Когда:** разбор инцидента/жалобы: найти ошибку, посмотреть хвост логов, собрать пакет для разработки.
**Как сейчас:** категории логов (Server, Catalina, Archive текущий/старый, Front, Franchise) + быстрые ссылки (error.log, full.log, JMS, startup, threaddump, кнопка «V» → Victoria Logs) + скачивание ZIP; архивные логи доступны при остановленном сервере.
**Источник:** US-019; DO-899; IIKOWEB «Работа с логами».
**Боли:** нет поиска по всем логам клиента за дни/месяцы и нет «бегущих» логов (tail -F) — «предварительное скачивание всех логов на свою машину — так себе идея»; при докачке перекачивается всё заново.
**Новому интерфейсу:** встроенный просмотр и поиск по логам, live-режим, диапазон дат, шаринг ссылкой, быстрый переход из карточки сервера.

## SC-09. Бэкап БД (в т.ч. на FTP, с анонимизацией)
**Роль:** L3, аналитики · **Частота:** часто
**Когда:** плановый/ручной бэкап перед изменениями; подготовка базы для разработки/партнёра.
**Как сейчас:** «Бекап БД»: тип файла (.bak/.dmp), папка, «Архивировать после», «Сделать бекап», «На FTP» (выбор euftp…), «Анонимизация», «Запустить после». Или «Бекап из файла»: поиск в АРХИВ/НОЧНЫЕ/ФАЙЛЫ. Результат — в окне логов; для партнёра создаётся папка на FTP в разделе «Обслуживание».
**Источник:** US-022; wiki: «Работа с бэкапами по FTP в XHOSM»; DEVOPS: «Выдача бекапов БД партнёрам».
**Боли:** поиск файла среди папок; анонимизация спрятана; списки бэкапов найдены, «но ссылки не открываются» (DO-899).
**Новому интерфейсу:** визард «сделать/найти/выдать» бэкап, история бэкапов сервера, живые ссылки, статус отправки на FTP.

## SC-10. Восстановление / перенос / копирование БД
**Роль:** L3 · **Частота:** часто/планово
**Когда:** потеря данных, переезд клиента, миграция между кластерами.
**Как сейчас:** «Восстановление»: выбрать файл → «Пересоздать БД» → «Восстановить» → «Запустить после». «Перенос/копирование»: SQL-сервер, БД, «Не изменять resto.prop», «Пересоздать БД», «Удалить исходную». Долгие операции — контроль по логам.
**Источник:** US-013/014; UC-009.
**Боли:** высокий риск (пересоздание/удаление исходной) с модальными подтверждениями; процесс долгий и без деталей.
**Новому интерфейсу:** превью плана операции («что будет сделано») до запуска, чек-поинты, прогресс, безопасный откат/бэкап-перед.

## SC-11. Кассовые смены: закрыть/удалить
**Роль:** L3, партнёры · **Частота:** часто
**Когда:** смена не закрылась (висит, битые данные), клиент/партнёр просит закрыть или удалить.
**Как сейчас:** остановить сервер («Служба» → «Остановить», дождаться STOPPED) → «Разное» → «Закрыть смену» (скопировать GUID и дату-время, скорректировать, «Ок») или «Удалить смену». Если смен несколько — снять галку автозапуска Tomcat; после — перезапустить Tomcat.
**Источник:** US-015; DO-969; wiki: «Закрытие смены (инструкция для партнёров)».
**Боли:** только по одной смене за раз: «удалить более 100 смен — по одной ну ооочень долго»; люди пишут SQL-скрипты в обход («кроме как обучить макрос, не понимаю как убрать эту рутину»); галочки массовости просят с 2022.
**Новому интерфейсу:** список смен сервера с массовыми галочками и датами, корректировка пачкой, шаблоны («закрыть всё до даты»), понятные предупреждения.

## SC-12. Демо-стенд для диагностики
**Роль:** L3, аналитики · **Частота:** часто
**Когда:** нужно воспроизвести проблему клиента, не трогая боевой сервер; проверить обмен/версию.
**Как сейчас:** создание через partners.iiko.ru (демо-кабинет) → сервер уходит в xHOSM (или вручную создать в xHOSM, поиск по UID) → выбрать версию → развернуть → восстановить бэкап клиента (с анонимизацией) → лицензия (боевая при больших объёмах). EU: сменить адрес на европейский через CRM.
**Источник:** US-003; wiki: «Демо стенды».
**Боли:** свои демо-серверы приходится каждый раз искать заново: «было бы удобно внести в избранные» (DO-1311); создание разнесено между кабинетами и xHOSM.
**Новому интерфейсу:** «Мои демо» с избранным и сроком жизни, шаблоны конфигураций, быстрый доступ к восстановлению бэкапа.

## SC-13. SQL-запросы по базе клиента
**Роль:** L3, аналитики · **Частота:** ежедневно
**Когда:** диагностика данных, разборы расхождений, точечные исправления.
**Как сейчас:** вкладка SQL: запрос, запуск, лимит 100 строк результата (далее CSV), флаг «Разрешить изменения» для записи на работающем сервере; массовый режим — до 1500 серверов. Макросы/готовые запросы лежат в базе знаний (в самом UI «Избранные SQL» не прижились).
**Источник:** US-004; BR-SQL; L3S: «Полезные методы запросов БД»; интервью.
**Боли:** рабочие запросы все пишут заново («привычка писать запросы заново»); предупреждение о записи на боевом не помогает понять последствия.
**Новому интерфейсу:** редактор с историей и общими сохранёнными запросами, пояснение последствий записи, безопасные пресеты частых диагностик.

## SC-14. Groovy-скрипты (фиксы на лету)
**Роль:** L3 · **Частота:** периодически
**Когда:** массовые однотипные исправления данных (например, проблемы BCrypt — «не пускает в веб-приложение»).
**Как сейчас:** вкладка Cloud Tools → «Обслуживание» → Groovy.jsp: выбор скрипта (например, Bcrypt part1/part2), запуск; применение до 5 минут; часть скриптов рестартит сервер.
**Источник:** US-005; wiki: «Проблема BCrypt хэшей».
**Боли:** запуск неочевиден (5-я вкладка), не видно прогресса и последствий, критичные скрипты среди прочих.
**Новому интерфейсу:** каталог скриптов с описанием эффекта и требований, прогресс применения, предупреждения о рестартах.

## SC-15. Обрезка базы (shrink) + пометка
**Роль:** L3 · **Частота:** периодически
**Когда:** база распухла, нужно урезать хранение до даты (по правилам: не позднее начала открытого периода − 1 год и т.д.).
**Как сейчас:** 7 шагов: ручной бэкап → остановить сервер → проверить период → в «Конфигурации» прописать db-shrink-no-backup=true и db-shrink-date → включить эксклюзивный режим (db-shrink-exclusive-mode=true) → дождаться успеха (Complete, балансы совпали) → вернуть обычный режим → пометить сервер комментарием (значок i).
**Источник:** wiki: «Обрезка/Shrink базы», «Пометка серверов после обрезки».
**Боли:** полностью ручной процесс с ручным вводом параметров в конфиг; ошибка может повредить данные (в логах различают «повредились/не повредились»); пометка — вручную через значок.
**Новому интерфейсу:** пошаговый мастер для shrink: проверка условий, параметры подставляются сами, контроль балансов, автопометка сервера.

## SC-16. Перевод RMS → Chain
**Роль:** L3 · **Частота:** периодически
**Когда:** клиент переходит на сетевое решение (Chain).
**Как сейчас:** 6 шагов: поиск CRM ID → скрипт №1 (репликация + стоп Tomcat) → бэкап БД RMS → создать Chain → развернуть БД из бэкапа → скрипт №2 (Server Instance) → запуск → при ошибке «Ревизия» → скрипт №3. Между шагами — проверки вручную.

**Новому интерфейсу:** мастер перевода с прогрессом по шагам, автопроверками и откатом; номера скриптов заменить на понятные названия.

## SC-17. Создание нового сервера (NSR)

## SC-23. Лицензии: «красный Cloud» — проверка UOC
**Роль:** L3 · **Частота:** периодически
**Когда:** в админ-панели облачко Cloud красное, обмен с UOC не сходится.
**Как сейчас (4 шага, дословно):**
1. «В xhosm: Обновить upRevision» — открыть xhosm, найти элемент, «Нажать upRevision → затем Обновить для него».
2. «В Postman: Вызвать execSyncWithCrm» — POST `http://uocservice.iiko.nltran.lan/api/TransportUoc/execSyncWithCrm`.
3. «В админке веба: Выполнить действия в UOC Organizations» — по очереди: *Synchronize, Flush UOC binding, Check credentials*.
4. «Проверка результата: если облачко стало зелёным — всё работает; если не стало — спросить про клаудные лицензии» (для МЕНА — свои менеджеры).
**Диагностика (сопутствующая, wiki 129651750):** хэш пароля «bcrypt сильно длиньше чем sha1 и в начале с долларами»; для чейнов — Groovy.jsp (Bcrypt part1, DO-1594); для одиночных РМС — либо тот же груви, либо без перезапуска `POST .../resetPasswordHashes`; проверки переопределений через GetPasswordOverrides / DeletePasswordOverrides; «Обновленный пароль придет с обменом РМС - ЕЦО в течение 10 минут».
**Источник:** wiki L3S 106593535, 129651750; DO-1594.
**Боли/контекст:** лечение одной жалобы снова в трёх системах (XHOSM → Postman → админка); часть — по инструкции на вики; ожидания по 10 минут.
**Новому интерфейсу:** расширить «лицензионный чек-лист» (SC-04) веткой UOC: состояние синхронизации, следующее действие, ожидание таймером.

## SC-24. Выдача бэкапа БД партнёру (FTP) и анонимизация для разработки
**Роль:** L3, аналитики · **Частота:** часто
**Когда:** партнёру/разработке нужна база клиента (из текущей БД или из архива/ночного бэкапа).
**Как сейчас (дословно по инструкции):** «XHOSM предоставляет возможность выдавать партнёрам БД клаудных серверов двумя способами: а) из текущей БД; б) из архива либо ночного бекапа». «Для выдачи БД партнёру необходимо установить флажок "на FTP-сервер". В этом случае: 1) файл БД будет помещён в специальную папку `\\mria\ftp\<СЕРВЕР>\`; 2) в сообщениях HOSSUPPORT будет указан FTP-сервер (ftp://cloud.iiko.ru), имя файла, логин и пароль для доступа; логин и пароль дублируются на почту запустившему бекапирование; 3) партнёр, используя предоставленный логин и пароль, подключается FTP-клиентом и скачивает файл». «При выкладывании каждого следующего файла выдаётся новый пароль. Партнёр видит и может скачать все файлы в папке».
**Анонимизация:** сервис backup-api (pgsql-anonymizer) — «сервис берет оригинальный дамп базы данных с реальными клиентскими данными, прогоняет его через алгоритмы маскирования и выдает безопасную копию»; развёрнут в docker, доступен по `http://backup-api.cloud.lan/docs`; задача DO-1917 — «добавить в XHOSM возможность при выдаче бэкапов заранее обратиться к сервису backup-api, получить анонимизированный бэкап и затем уже выдать его».
**Источник:** wiki DEVOPS 81464878; DORMS 168101625; задачи DO-1917, DO-1181, DO-536.
**Боли/контекст:** «Тратится много времени на скачивание (+распаковку) бэкапов от партнеров… лучше бы сделать загрузку бэкапов через партнерский кабинет» (DO-1181); выдача MSSQL-бэкапа из архива раньше была «нетривиальна, привлекается слишком много людей» (DO-536).
**Новому интерфейсу:** мастер «выдать данные»: кому, что, с анонимизацией или нет, статус доставки на FTP, автоистечение доступов.

**Как сейчас:** при выборе типа контракта на портале создаётся задача в Pyrus с набором параметров: «Ресторан — для которого необходимо развернуть хостинг; Тип заявки — Запрос на обслуживание; Тип запроса на обслуживание — Создание хостинга; Срок создания; Time zone; Clusterid — "1" или "3" (RU-клауд, DE-клауд); Locale — "ru-RU", "en-GB"; Timezone — "Europe/Moscow"…» (IA-1022, Готово). Полная автоматика — в работе: IA-1070 (Открытый, 2020): «На партнерском портале сейчас нельзя развернуть RMS → Expected: можно»; DO-405 — «Автоматический сценарий развертывания РМС cloud».
**Источник:** задачи IA-1022, IA-1070, DO-405; IA-4235/IA-4306 (обновление демо-стендов из портала).
**Боли/контекст:** долгие годы перехода к самообслуживанию; порталу нужны те же проверки, что и xHOSM (см. ТЗ «Развернуть сервер»: сообщения об ошибках, валидация домена).

## SC-28. Эскалация заявок: боты Pyrus (сценарии 1–3 + блокирующие/критические)
**Роль:** поддержка, боты · **Частота:** постоянно
**Когда:** заявка вовремя не берётся/не отвечается — включается автоэскалация.
**Как сейчас (по задачам DO-755/776/781/878):**
- «Сценарий 1. SPRT поле в Pyrus»: добавить в Pyrus поле «Задача в JIRA», связать с проектом SPRT, получать изменение статуса задачи.
- «Сценарий 2» (бот в роли Эскалация): «При добавлении в форме… роли Эскалация, добавлять в задачу роль… Удалять роль Эскалация»; механизм — через вебхук (без парсинга списков), очередь задач, ошибки логируются.
- «Сценарий 3» (Готово): при условиях (роль «Эскалация», статус «В работе»/«В команде», тип заявки ≠ Доработка, Модуль ≠ API, приоритет Блокирующий/Критический/Важный или iikoCloud=1, последний ответ от iiko > 3 часов) — «добавлять URL задачи в произвольный телеграмм канал»; при «Прочитана»/снятии роли — удалять запись.

**Новому интерфейсу:** это процесс поддержки (не экран xHOSM), но связан: статусы и «модуль» заявок используются в сценариях; при редизайне — учитывать связку «заявка ↔ сервер».

## SC-29. Автообновление сервера по заявке (Pyrus-форма → CRON XHOSM)
**Роль:** партнёры, бот · **Частота:** периодически
**Когда:** партнёр хочет обновить сервер по заявке, без ручного вмешательства поддержки.
**Как сейчас (DO-703, Готово):** «Создаем в Pyrus отдельную форму с реквизитами MVP (в объем входят только отдельно стоящие РМС): Ресторан; Версия на которую обновляем; Дата и Время; Номер задания из XHOSM (не редактируемый); Кнопка "Отменить обновление"; статический текст с инструкцией. При создании в заявку добавляется бот. Бот создает в CRON XHOSM задание на обновление. При успешном задании заполняется реквизит "Номер задания"; в комментарии — "Задание на обновление создано успешно". После успешного обновления — "Обновление прошло успешно". Если не успешно — код ошибки и команда "Партнерская поддержка"».
Обсуждение: «поле ресторан не всегда можно выбрать, лучше взять поле дилер и поле UID… проверять относится ли этот клиент к этому дилеру»; ответ Сухих: «Не лучше. И сложнее логика. Вот так Лемма случайно обновит Чейн Андерсона».
**Источник:** задача DO-703.
**Боли/контекст:** связка «заявка ↔ задание планировщика» есть, но частичная (только отдельные РМС, не сети).
**Новому интерфейсу:** видимая связь «заявка/задание/сервер», отмена и статусы — часть центра задач (SC-18).

## SC-30. Автоконтроль состояния: очередь продаж, память, уведомления CRM→XHOSM
**Роль:** автоматика, дежурные · **Частота:** постоянно
**Когда:** фоновая автоматика ловит типовые проблемы раньше заявок.
**Как сейчас:**
- «Находить и сообщать о застрявшей очереди продаж» (DO-739, Готово): «типовой сценарий: застревает очередь продаж; ресторан этого не замечает сразу и не сообщает в техподдержку; ресторан в Беке не видит данных Фронта; разрастается full.log» → «ежедневно проверять error.log клиентов на наличие записи `frontUpdate.importFrontData`… Если такая запись есть, отправить алерт в Telegram или лучше — создать заявку в Pyrus» (метод `pyruscreate` с crmid, заголовком, текстом, типом, приоритетом).
- Автоуправление памятью (DO-513, DO-710, Сделать): «Выявить закономерности для разработки автоматических сценариев; Формировать список РМС и список действий по ним»; правило: «Max memory > memory_crm and total memory < Max memory and uptime > 30 → Max memory = total memory».
- Уведомления CRM→XHOSM (IA-994, Готово): «Клиент проплачивает расширенный период… о которых HOSM/XHOSM узнает только на след. день» → метод `crminfoupdated`; «При неоплате расширения ставится дефолтное значение 60».
**Источник:** задачи DO-739, DO-513, DO-710, IA-994.
**Боли/контекст:** автоматика принимает решения за людей — нужна видимость «что автоматика сделала/сделает».
**Новому интерфейсу:** витрина автопроверок и их результатов (журнал автоматики), чтобы поддержка видела, почему сервер изменился сам.

## SC-31. Массовые действия по мониторингу и поиск «по истории» (Prometheus, WHERE)
**Роль:** L3, инфра · **Частота:** периодически
**Когда:** нужно массовое действие по данным мониторинга; сложные выборки по истории.
**Как сейчас:**
- Экспорт из Prometheus (76252374): «Зачастую на основании данных мониторинга нужно произвести массовое действие во внешней системе (например, Xhosm). Тогда такой нестандартный формат вызывает неудобства» → полученный результат в notepad++ обрабатывают регуляркой `(.*?)client="(.*?)"(.*$)` → получают «чистый список значений свойств, пригодный к использованию в Xhosm».
- Сложный поиск в XHOSM (70387125, «Команды и атрибуты»): WHERE + условия; примеры: «Ищем Чейны, в составе которых более 10 РМС»; «Ищем сервера, у которых "сервисное окно" в 16-00 МСК»; «Кого когда обновляли / переносили / архивировали и восстанавливали / добавляли память / бекапили / пересоздавали службы»; «Сервера остановленные и не имеющие событий за последние 30 дней»; сортировки `ORDER BY db_size / last_restarted / memory_crm DESC`.
**Источник:** wiki DEVOPS 76252374, 70387125.
**Боли/контекст:** мониторинги и xHOSM — два мира; перенос списков руками через редактор.
**Новому интерфейсу:** «мониторинг → действие» без ручной обработки; конструктор условий и истории (перекликается с SC-01).

## SC-32. Восстановление серверов из архива после просрочки оплаты
**Роль:** партнёр, L3 · **Частота:** по ситуациям
**Когда:** клиент просрочил оплату — серверы ушли в архив; после оплаты нужно поднять.
**Как сейчас (дословно по инструкции):**
- **Автоматика:** «Чтобы сервера восстановились из архива после просрочки оплаты автоматом хостинга нужно в ЛК чейн: Зайти в распределение лицензий → Удалить лицензии с РМС, сохранить → Распределить заново, сохранить. Это даст команду автоматике на запуск серверов после просрочки. Сервера поднимаются в течении часа после данной операции (обычно восстановление занимает 10–15 минут)».
- **Если не сработала автоматика:** «В Xhosm найти сервер по его crmid \ uid \ domain → Выделить сервер галочкой → На 3 вкладке Xhosm выбрать блок "Архив" > Восстановление (параметр лучше оставить Авто и галочка "Запустить")».
**Источник:** wiki L3S 62196458; задачи DO-539 (кросскластерное восстановление), DO-1701 (сервер ушёл в архив, несмотря на событие активации).
**Боли/контекст:** «партнеры не знают на какое время установилась задача о поднятии сервера (или вывода из архива) и установилась ли вообще» (DO-1676); бывают случаи, когда автоматика не срабатывает (DO-1701).
**Новому интерфейсу:** прозрачность «почему сервер в архиве и что его поднимет»; видимая цепочка «оплата → лицензии → задача → запуск» (перекликается с DO-1676).

## SC-33. «Глобальный помощник»: ИИ-бот через API XHOSM
**Роль:** клиенты, ИИ-бот · **Частота:** новая механика 2026
**Когда:** «Клиент любого дилера обращается в "Глобального помощника"».
**Как сейчас (задачи DO-1924/DO-1925, Готово, май 2026):**

**Боли/контекст:** xHOSM становится источником данных/действий для внешних ИИ-каналов (через API) — контур без человеческого UI.
**Новому интерфейсу/архитектуре:** продумать API-контур и аудит действий бота (кто/зачем/что сделал) — рядом с «доказательным статусом».

# ЧАСТЬ 4. Сквозные требования к новому интерфейсу (из сценариев)

1. **Поиск — главный вход, а не строчка в углу.** Распознавание типа ввода, подсказки, сохранённые запросы, связи Chain↔RMS, пакетные действия.
2. **Статус должен быть достоверным и проверяемым.** Источник, время проверки, история, честные «данные устарели».
3. **Любая долгая операция — прозрачна.** Этапы, прогресс, ETA, результат, уведомление (очереди и тех.окна — часть этого паттерна).
4. **Единый центр задач и уведомлений.** Планировщик, очередь, активные операции, аудит — в одном месте (закрывает в т.ч. DO-427).
5. **Массовость вместо рутины.** Смены, лицензии, рестарты, скрипты — везде, где сейчас «по одной штуке».
6. **Карточка клиента на одном экране.** Контракт, дилер, лицензии, UID, iikoUser, память, период, история — без походов в CRM/Postman/админку.
7. **Безопасность с объяснением.** «Почему нельзя» и «что сделать» вместо серых кнопок; подтверждения; аудит.
8. **Права — видимы и объяснимы.** Скрывать/блокировать по ролям, показывать причину отсутствия действия.
9. **Избранное и сохранёнки — переосмыслить.** Демо-серверы, SQL, выборки: то, что «не прижилось» — это провал UX, а не пользователей.
10. *(v2)* **Сквозные потоки через несколько систем — сводить в один маршрут.** Примеры: лицензия/Cloud (XHOSM → Postman → админка веба, SC-04/SC-23), франшиза (RESTOPROPPACK → БД → ЛК, SC-21/22), база для партнёра (XHOSM → FTP → инструкция, SC-24), выпуск версий (TeamCity → XHOSM → GitLab → FTP, SC-25).
11. *(v2)* **Сервисные процессы — часть системы, а не набор инструкций на вики.** Пошаговые мастера и чек-листы (shrink, перевод в Chain, франшиза, выдача данных), видимые статусы шагов. **Автоматику — на витрину.** Показывать, что система сделала сама (SC-30) и что запланировано (SC-18).
